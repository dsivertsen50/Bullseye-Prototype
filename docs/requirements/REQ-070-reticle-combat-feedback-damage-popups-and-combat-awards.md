# REQ-070 — Reticle Combat Feedback, Damage Popups, and Combat Awards

## Summary

Add a lightweight combat-feedback system near the player's reticle that immediately communicates successful damage, eliminations, and notable combat achievements.

Examples:

- `+2`
- `+8  ELIMINATION`
- `BULLSEYE ELIMINATION`
- `DOLPHIN DIVE`
- `DETACHED BULLSEYE`
- other future combat awards

The purpose is to provide the satisfying immediate feedback common in multiplayer shooters without cluttering the HUD.

The feedback should appear near the center of the screen, close to—but not directly on top of—the reticle.

The visual style should be:

- small
- italicized
- white text
- red outline
- red outline should use the same red used by the Bullseye visual identity
- readable against both bright and dark environments
- brief and unobtrusive

The system must work correctly in multiplayer and should be designed so additional awards can easily be added later.

---

# 1. Goals

Implement a reusable HUD combat-feedback system capable of displaying:

1. Damage/score feedback when the player successfully damages another player.
2. Elimination feedback.
3. Special combat awards.
4. Multiple related events occurring nearly simultaneously.
5. Multiplayer-authoritative results.
6. Configurable display values rather than hard-coded numbers.

This should feel similar to the small score notifications that appear near the reticle in many multiplayer shooters.

---

# 2. Basic Damage Feedback

Whenever the local player successfully damages another player, display a small numeric popup near the reticle.

Example:

```text
+2
```

or

```text
+10
```

The displayed number must come from the actual gameplay event.

Do NOT simply hard-code:

```text
+10
```

The system should be capable of displaying whatever value is appropriate based on the weapon, damage event, or scoring rules.

For example:

- pistol hit
- shotgun pellet/damage event
- AK hit
- sniper hit
- grenade damage
- rocket damage
- future weapons

should all be able to send their actual value to the HUD feedback system.

---

# 3. Damage vs. Score Architecture

Do not unnecessarily couple this HUD system to a specific scoring model.

Create a generic combat feedback API such as conceptually:

```csharp
ShowCombatFeedback(...)
```

that can receive information such as:

```text
amount
feedbackType
awardType
optionalText
priority
```

The system should be able to eventually support either:

```text
+10 points
```

or:

```text
+2 damage
```

depending on how our scoring system develops.

For the current implementation, use the value already generated by the relevant damage/scoring system wherever possible.

Avoid duplicating damage calculations inside the HUD.

The HUD should DISPLAY gameplay results, not calculate them.

---

# 4. Standard Elimination Feedback

When the local player eliminates another player, provide stronger feedback than a normal hit.

Example:

```text
+8  ELIMINATION
```

or, depending on the current scoring architecture:

```text
ELIMINATION
```

If an associated score is available, it may be displayed with the elimination.

Example:

```text
+10  ELIMINATION
```

The exact score value should remain configurable.

---

# 5. Special Combat Awards

The system must support named combat awards.

Initial awards should include at minimum:

### Dolphin Dive Elimination

Award when the player eliminates another player by performing the dolphin-dive/body-slam mechanic.

Example:

```text
DOLPHIN DIVE
```

---

### Detached Bullseye Elimination

Award when the player eliminates an opponent by destroying/shooting their Bullseye while that Bullseye is physically detached from the player's body.

Example:

```text
DETACHED BULLSEYE
```

or:

```text
BULLSEYE ELIMINATION
```

Choose whichever terminology best matches the existing gameplay terminology, but make the displayed string configurable.

---

# 6. Award System Must Be Extensible

Do not create special HUD logic individually for every award.

Create an extensible award/event structure so future events can be added easily.

Potential future awards might include:

- headshot elimination
- ricochet elimination
- long-distance elimination
- grenade elimination
- rocket elimination
- elimination immediately after Bullseye detachment
- sniper elimination
- multi-elimination
- revenge
- assist
- airborne elimination
- environmental elimination
- magnetism grenade-related award

These DO NOT all need to be implemented in REQ-070.

The architecture simply needs to make adding them easy.

A centralized enum/data definition would be appropriate, for example conceptually:

```csharp
CombatAwardType
{
    None,
    Elimination,
    DolphinDive,
    DetachedBullseye
}
```

with room to expand later.

---

# 7. Visual Design

The combat feedback should appear close to the reticle.

It should NOT obscure the reticle itself.

Suggested positioning:

```text
             RETICLE

                +

             +10
          ELIMINATION
```

or slightly offset to one side/below the reticle if that provides better visibility.

Exact positioning should be exposed in the UI so we can easily adjust it later.

---

# 8. Font Styling

Combat feedback text should use the following visual style:

### Font

- italicized
- relatively small
- clean
- readable
- visually consistent with the rest of the game's HUD

### Main Color

White.

Example:

```text
#FFFFFF
```

### Outline

The text should have a red outline.

The red should match the game's existing Bullseye red color.

Do NOT independently choose an unrelated red if an existing Bullseye color/material/color constant can be referenced.

Where practical, create or reference a shared Bullseye-red UI value so the HUD branding remains visually consistent.

---

# 9. Readability

The purpose of the red outline is to keep the white text visible regardless of map lighting.

It should remain readable against:

- bright sky
- snow/light surfaces
- dark walls
- shadows
- colorful environments
- explosions/effects

The outline should be visible enough to separate the text from the environment without making the text appear large or cartoonishly thick.

Use TextMeshPro outline functionality if appropriate.

---

# 10. Animation

The feedback should feel responsive but subtle.

Suggested behavior:

1. Event occurs.
2. Text appears quickly.
3. It remains visible briefly.
4. It gently moves upward and/or fades.
5. It disappears.

Example approximate behavior:

```text
appear
↓
remain for ~0.5–1.0 seconds
↓
slight upward movement
↓
fade out
```

Exact duration should be configurable.

Do not use a large dramatic animation for ordinary damage.

Special awards may remain visible slightly longer than basic damage notifications.

---

# 11. Multiple Hits

The system must handle rapid weapon fire.

For example, firing an AK should not cause the UI system to fail because many successful hits occur close together.

Determine a reasonable strategy such as:

### Option A — Individual feedback

```text
+2
+2
+2
```

with small stacked/fading notifications.

### Option B — Accumulating feedback

Rapid hits within a very short window could accumulate:

```text
+2
```

becomes:

```text
+4
```

then:

```text
+6
```

This may create a cleaner HUD.

Prefer an architecture that allows us to tune this behavior.

For the initial implementation, choose whichever is cleaner and simpler while ensuring rapid-fire weapons do not create excessive HUD clutter.

---

# 12. Simultaneous Damage + Award

A combat event may generate multiple pieces of information.

For example:

```text
+8
ELIMINATION
DOLPHIN DIVE
```

Do not place several independent UI objects directly on top of one another.

The system should coordinate related feedback.

One acceptable presentation might be:

```text
+8  ELIMINATION
DOLPHIN DIVE
```

Another:

```text
+8
ELIMINATION
DOLPHIN DIVE
```

The exact layout can be tuned during testing.

---

# 13. Priority

Different feedback types should have different importance.

Suggested hierarchy:

```text
Special Award
    >
Elimination
    >
Damage
```

For example, a standard `+2` hit should not visually overwhelm:

```text
DOLPHIN DIVE
```

Special events can remain visible slightly longer or appear as a second line.

Keep all of the feedback relatively small.

---

# 14. Multiplayer Requirements

Combat feedback should only be displayed to the player responsible for the relevant action.

Example:

Player A shoots Player B.

Player A sees:

```text
+2
```

Player B should NOT see Player A's score notification.

Player C should NOT see it either.

Likewise:

Player A performs a dolphin-dive elimination on Player B.

Player A sees:

```text
ELIMINATION
DOLPHIN DIVE
```

The award should be generated from an authoritative gameplay result rather than merely predicting that an elimination occurred locally.

---

# 15. Avoid Duplicate Notifications

Because Bullseye uses Netcode for GameObjects, ensure networking does not cause duplicate feedback.

One combat event must not result in:

```text
+2
+2
```

because both client-side and server-side callbacks independently reported the same hit.

Establish a clear ownership/event path.

Prefer:

```text
Authoritative gameplay result
        ↓
Notify responsible local player
        ↓
CombatFeedbackHUD
        ↓
Display UI
```

The HUD itself should contain no network authority logic.

---

# 16. Interaction With Existing Telemetry

REQ-070 should integrate cleanly with the telemetry work introduced in previous requirements.

The visual feedback system should not independently infer whether something was:

- a dolphin-dive elimination
- detached Bullseye elimination
- normal elimination

if the gameplay system already knows that information.

Instead, the gameplay event should provide the relevant classification.

Conceptually:

```text
Combat event occurs
       ↓
Gameplay resolves event
       ↓
Telemetry records event
       ↓
HUD receives appropriate feedback event
```

Telemetry and HUD feedback should therefore describe the same underlying event.

Do NOT make the HUD the source of truth for telemetry.

---

# 17. Recommended Component Structure

Cursor should inspect the existing HUD architecture before choosing final class names.

A likely structure might include:

```text
CombatFeedbackHUD
CombatFeedbackItem
CombatFeedbackEvent
CombatAwardType
```

Potential responsibilities:

### CombatFeedbackHUD

Receives events and manages:

- spawning notifications
- positioning
- stacking
- timing
- animation
- cleanup

### CombatFeedbackItem

Represents one visible feedback item.

Handles:

- text
- amount
- award
- animation
- fade

### CombatFeedbackEvent

Data describing the gameplay result.

Potential fields:

```csharp
float amount;
CombatFeedbackType type;
CombatAwardType award;
string customText;
```

These are architectural suggestions only.

Cursor should reuse the existing Bullseye systems where appropriate rather than creating redundant systems.

---

# 18. Performance

Do not repeatedly instantiate/destroy large numbers of UI objects unnecessarily during automatic weapon fire.

If useful, implement lightweight pooling for feedback UI elements.

The system should comfortably support:

- automatic weapons
- shotgun hits
- multiple players
- rapid eliminations
- grenade/rocket splash damage

without meaningful performance impact.

---

# 19. Inspector Configuration

Expose important presentation settings in the Inspector.

Suggested settings:

```text
Damage Text Duration
Award Text Duration
Fade Duration
Vertical Offset
Reticle Offset
Font Size
Outline Width
Bullseye Red
Stack Spacing
Maximum Simultaneous Messages
Rapid-Hit Accumulation Window
```

Do not bury basic visual tuning inside hard-coded constants.

---

# 20. Scope Boundaries

REQ-070 DOES include:

- reticle-adjacent damage feedback
- elimination feedback
- combat award feedback
- dolphin-dive elimination award
- detached-Bullseye elimination award
- multiplayer-safe event delivery
- visual styling
- animations
- rapid-hit handling
- extensible architecture

REQ-070 DOES NOT require:

- redesigning the scoreboard
- lifetime statistics
- rewriting weapon damage
- rewriting Bullseye health
- implementing every possible future medal
- adding announcer voice lines
- creating a Halo-style medal system
- changing existing telemetry definitions unless required to expose an already-known combat event

---

# 21. Acceptance Criteria

REQ-070 is complete when:

- [ ] Successfully damaging an opponent produces visible feedback near the reticle.
- [ ] The displayed amount comes from the actual gameplay event rather than a hard-coded `+10`.
- [ ] The feedback belongs only to the player responsible for the damage.
- [ ] Eliminating another player produces elimination feedback.
- [ ] A dolphin-dive elimination produces a `DOLPHIN DIVE` award.
- [ ] Eliminating a detached Bullseye produces a dedicated Bullseye award.
- [ ] Special awards can be extended later without rewriting the HUD.
- [ ] Text is relatively small and italicized.
- [ ] Main text is white.
- [ ] Text has a red outline.
- [ ] The red visually matches the Bullseye red.
- [ ] Text remains legible against both light and dark environments.
- [ ] Feedback appears near but does not cover the reticle.
- [ ] Feedback fades/disappears automatically.
- [ ] Rapid-fire weapons do not flood or break the HUD.
- [ ] Multiple related events are laid out without overlapping.
- [ ] Multiplayer does not generate duplicate notifications.
- [ ] The HUD displays authoritative gameplay outcomes.
- [ ] HUD events align with the underlying gameplay/telemetry classification.
- [ ] Major presentation variables are configurable through the Inspector.
- [ ] Existing combat, weapon, Bullseye, HUD, and multiplayer functionality remains intact.

---

# 22. Testing Checklist

Test at minimum:

### Standard Damage

1. Shoot another player with a pistol.
2. Confirm a small numeric notification appears near the reticle.
3. Confirm only the shooter sees it.

### Automatic Weapon

1. Shoot another player repeatedly with the AK.
2. Confirm rapid damage notifications remain readable.
3. Confirm notifications do not indefinitely accumulate.

### Shotgun

1. Fire a shotgun at another player.
2. Confirm multiple pellet/damage events do not produce broken or excessive UI behavior.

### Elimination

1. Eliminate another player normally.
2. Confirm elimination feedback appears.

### Dolphin Dive

1. Eliminate another player using the dolphin-dive/body-slam mechanic.
2. Confirm:

```text
DOLPHIN DIVE
```

appears.

### Detached Bullseye

1. Cause another player's Bullseye to detach.
2. Eliminate the Bullseye while detached.
3. Confirm the dedicated detached-Bullseye award appears.

### Multiplayer

Test with at least two players.

Confirm:

- shooter gets feedback
- victim does not get the attacker's feedback
- other players do not get the attacker's feedback
- one hit produces one feedback event
- one elimination produces one elimination result

### Lighting

Test the UI against:

- bright background
- dark background
- sky
- interior
- red/brown surfaces

Confirm the white text/red outline remains easy to read.

---

# 23. Desired Result

Successful combat should now provide immediate visual confirmation near the reticle.

Ordinary interactions should feel lightweight:

```text
+2
```

Eliminations should provide stronger confirmation:

```text
+8  ELIMINATION
```

And unusual gameplay actions should be celebrated:

```text
DOLPHIN DIVE
```

or:

```text
DETACHED BULLSEYE
```

The end result should make combat feel more responsive and rewarding while preserving Bullseye's clean HUD and establishing a reusable foundation for a larger combat-award system later.
